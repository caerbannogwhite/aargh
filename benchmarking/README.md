# enchanter benchmarking

Cross-library performance comparison, following the
[h2oai db-benchmark](https://github.com/h2oai/db-benchmark) methodology. The
goal is not to beat Polars — it's to keep enchanter honest and to catch
regressions as the library's performance work lands.

Current scope: **Q1 of the groupby task — `sum(v1) group by id1`** — on the G1
datasets (10M-row file has 100 distinct `id1` groups). More questions can be
added over time.

## Latest results (Q1: `sum(v1) by id1`)

Groupby of already-in-memory data (CSV read excluded). Recorded on a 16-core
machine; single point-in-time snapshot; see caveats. Times in **milliseconds**.

| solution | version | 1e6 rows | 1e7 rows |
| --- | --- | ---: | ---: |
| **enchanter — parallel hash-agg (0.4.0 spike)** | 0.4.0-spike | **1.94** | **15.5** |
| polars | 1.43.2 | 5.78 | 43.2 |
| data.table | 1.18.4 | 9.81 | 138 |
| enchanter — current groupby | 0.3.0-dev | 18.7 | 269 |
| dplyr | 1.2.1 | 31.3 | 515 |
| pandas | 3.0.5 | 49.4 | 512 |

Raw rows with versions live in [`data/results.tsv`](data/results.tsv).

### Reading it

- **enchanter's *current* groupby already beats pandas and dplyr**, and sits
  ~3–6× behind Polars/data.table — respectable for a pure-Go library.
- The **parallel hash-aggregation spike** (a 0.4.0 prototype, see
  [`gospike/`](gospike/RESULTS.md)) is the **fastest measured** here — ~2.8×
  faster than Polars at 1e7 — which is why 0.4.0 headlines "make it fast."
  This is the *ceiling* the pattern reaches, not the shipped number (see
  caveats).

## Running it

```sh
# R (dplyr + data.table)
cd benchmarking && Rscript bench_r.R

# Python (polars + pandas) — isolated venv, does not touch global Python
cd benchmarking
python -m venv .venv
.venv/Scripts/python -m pip install polars pandas   # POSIX: .venv/bin/python
.venv/Scripts/python bench_py.py

# enchanter (Go) — current groupby + the parallel hash-agg spike
go test ./benchmarking/gospike/ -run '^$' -bench 'GroupBy' -benchmem -benchtime=1s
```

Each script prints tab-separated `solution version rows question time_sec` rows;
`data/results.tsv` is the collected snapshot. All read the `testdata/G1_*.csv`
datasets, which are generated by `groupby-datagen.R` (driven by `gen.ps1`) and
are git-ignored (up to ~500 MB).

## Method & caveats

- **What's timed:** the groupby-aggregate on an already-loaded frame, CSV read
  excluded, for every library. R and Python use adaptive wall-clock timing
  (run enough iterations that total time is well above the OS timer resolution,
  then average — Windows `proc.time()` can't resolve sub-10 ms ops). enchanter
  uses Go's `testing.B`. Methodologies are close but not identical; treat these
  as directional, not publication-grade.
- **The spike is a specialized kernel.** It times the aggregation given
  pre-extracted key/value slices (`[]*string` keys, `[]int64` values) and
  exploits enchanter's string interning to hash by pointer. A real 0.4.0
  implementation must also handle multi-key groups, typed/int keys, all
  aggregates (mean/min/max/std/count), null keys, and building the result frame
  — so it will land somewhat slower than the raw spike. The pointer-key trick is
  specific to string keys.
- **Q1 only, one machine.** Single string key, 100 groups, `sum`. Not a general
  benchmark; other questions (multi-key, joins, filters, more aggregates) and
  other hardware will differ.
- `data/notes.md` is the older narrative from the pre-rename era (Gandalff,
  Polars 0.17 / pandas 1.3) — kept for history, superseded by the table above.
